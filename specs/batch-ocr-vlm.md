# 大批量站牌 OCR + VLM 复核流水线规格

> 状态：ready-for-agent  
> 来源：当前对话与现有站牌识别代码的现状梳理  
> 说明：当前项目未配置 issue tracker，本规格先作为本地规格文件保存。

## Problem Statement

现有站牌识别流程是单张海报、单站点脚本化的：版面切块、RapidOCR 识别、站名修正、双向校验和导出分散在多个入口中。面对约 20GB 的全量底板时，操作人员需要手工分批、反复重跑，无法可靠地知道哪些图已经完成、哪些失败、哪些需要复核。

同时，OCR 在极窄竖排文字、形近字、字符粘连和括号备注上仍会产生少量错误；直接把整张海报交给视觉大模型又存在图片被降采样、密集竖排被合并、输出长度截断、幻觉和成本不可控的问题。现有流程缺少一个可断点续跑、可缓存、可限流、能把 OCR 与 VLM 各自放在合适位置的批量生产能力。

## Solution

构建一条面向约 20GB 全量底板的批量流水线：

- 本地继续负责版面理解：路线块、站名行、站名列、动态画布打包。
- OCR 作为主识别链路，支持本地 RapidOCR 与远程 OCR 后端切换；远程只接收裁片或画布，不接收整张海报。
- VLM 作为复核链路，只处理低置信度、跨列、下站不一致、双向不一致、新模板和抽样 QA 等异常样本，不直接替代全量 OCR，也不静默覆盖 OCR 结果。
- 用 manifest 和任务队列管理全部海报与阶段状态，支持断点续跑、失败重试、重复图片去重和缓存。
- 输出每张海报的结构化 JSON、统一汇总结果、优先复核队列和可追溯的 OCR/VLM/人工来源标记。
- 支持约 1600 张海报的流式处理，不把 20GB 数据一次性读入内存。

## User Stories

1. 作为数据运营人员，我希望指定一个包含全量站牌 JPG 的目录就能启动批处理，以便不用手工拆分文件夹和逐个站点执行脚本。
2. 作为数据运营人员，我希望系统在启动时扫描目录并生成 manifest，记录每张图片的路径、哈希、站点、方向、大小和状态，以便随时知道全量任务的边界。
3. 作为数据运营人员，我希望内容完全相同的重复图片只处理一次，以便避免重复 OCR 和重复计费。
4. 作为数据运营人员，我希望看到每张海报处于 pending、layout_done、ocr_done、validated、vlm_review、done 或 failed 中的哪个状态，以便判断整体进度。
5. 作为数据运营人员，我希望进程中断后可以从上次完成的阶段继续，以便不用从头重跑整个 20GB 数据集。
6. 作为数据运营人员，我希望只重跑失败或未完成的海报，以便修复个别坏图时不影响已完成的成果。
7. 作为数据运营人员，我希望系统逐张流式读取图片，以便处理 20GB 数据时不会耗尽内存。
8. 作为数据运营人员，我希望每张海报完成后立即落盘，以便后续失败不会丢弃前面已经完成的结果。
9. 作为开发人员，我希望 OCR 通过统一后端接口接入，以便本地 RapidOCR 和远程 OCR 可以互换而不改版面逻辑。
10. 作为开发人员，我希望远程 OCR 只接收本地切好的画布或裁片，以便保持本地列映射和业务校验的单一事实来源。
11. 作为开发人员，我希望画布按实际列宽和列数动态打包，而不是固定八列，以便在准确率和请求数之间取得平衡。
12. 作为开发人员，我希望站名列和紧跟其后的备注列尽量留在同一个画布，以便避免备注被远程单独识别后挂错站。
13. 作为开发人员，我希望批量画布识别失败或检测框跨列时自动退回单列 OCR，以便保留现有 fallback 的纠错能力。
14. 作为运维人员，我希望本地 OCR、远程 OCR 和 VLM 分别有独立的并发与限流配置，以便慢速 VLM 不会阻塞全量 OCR。
15. 作为运维人员，我希望远程请求支持超时、重试、指数退避和熔断，以便供应商抖动时不会形成重试风暴。
16. 作为运维人员，我希望远程服务不可用时自动回退本地 OCR，以便整批任务不会因为单点故障而停止。
17. 作为运维人员，我希望缓存按海报、路线块、画布和 VLM 裁片分层，以便重跑和增量任务可以跳过已完成的工作。
18. 作为开发人员，我希望缓存 key 包含图片哈希、管线版本、打包参数、OCR 参数、模型版本和提示词版本，以便配置变化时不会误用旧缓存。
19. 作为数据运营人员，我希望系统自动校验当前站、下站和双向站序，以便把明显不一致的记录优先暴露出来。
20. 作为数据运营人员，我希望低置信度、跨列、下站不一致、双向不一致和新模板等情况被标记为异常，以便复核工作有明确优先级。
21. 作为复核人员，我希望只把异常站名裁片和必要上下文发给 VLM，以便控制成本并减少无关信息干扰。
22. 作为复核人员，我希望 VLM 输入包含目标裁片、前后站、线路号、表头下站和开往方向，以便模型有足够上下文判断竖排文字和备注。
23. 作为复核人员，我希望 VLM 只返回结构化意见，不直接修改最终数据，以便 OCR 与 VLM 的冲突可以被审计。
24. 作为复核人员，我希望 OCR 与 VLM 一致时自动通过，不一致时进入人工复核并保留两份结果，以便既不扩大人工量又不丢失疑点。
25. 作为复核人员，我希望 VLM 返回非法格式、空结果或低置信度时被忽略，以便错误输出不会污染主数据。
26. 作为复核人员，我希望复核队列按原因、置信度和线路重要性排序，以便先处理最可能影响数据的记录。
27. 作为复核人员，我希望能看到每个最终站名的来源是 OCR、VLM 还是人工修正，以便追溯数据是如何确定的。
28. 作为复核人员，我希望人工修正按图片哈希、线路和站序持久化，以便图片重命名或重跑后仍能复用修正结果。
29. 作为数据运营人员，我希望抽样调用 VLM 对 OCR 结果做独立 QA，以便发现系统性错字而不是只盯着低置信度样本。
30. 作为数据运营人员，我希望按站点或海报导出结构化 JSON，并能继续交给现有分析器生成 Excel、CSV 和报告，以便不破坏现有交付流程。
31. 作为数据运营人员，我希望看到每张海报和每个阶段的耗时、缓存命中、重试次数、VLM 调用次数和失败原因，以便评估全量任务的成本和稳定性。
32. 作为运维人员，我希望 API 密钥只从环境变量或密钥管理读取，不写入代码、日志或规格文件，以便避免凭据泄露。
33. 作为开发人员，我希望遇到无法识别的新模板时只标记为异常并保留原图/裁片，而不是让整批任务失败，以便后续单独处理新模板。
34. 作为开发人员，我希望损坏图片、空图片和缺字段图片被隔离并记录错误，以便坏数据不会阻塞其他海报。
35. 作为数据运营人员，我希望支持只跑指定站点、指定线路或指定海报子集，以便增量新增和问题复现。

## Implementation Decisions

### 最高验收缝

- 以批量入口作为最高验收缝：`run_batch(源目录或 manifest, 配置)` 负责完整批量流程，并返回可检查的批次报告。
- OCR 后端和 VLM 复核器通过依赖注入接入，作为可替换适配器，不作为独立验收缝。
- 单张海报解析、画布打包、缓存和状态机在批量入口内部完成，测试通过批量入口观察外部行为。

### 批处理编排

- 使用 SQLite 作为 manifest 和任务状态存储，启用 WAL 以支持多 worker 并发读写。
- manifest 以图片内容 SHA-256 作为主键，不以文件名、路径或修改时间作为身份。
- 任务状态机为：pending → layout_done → ocr_done → validated → vlm_review（可选）→ done；任一步失败进入 failed 并记录原因。
- 每张海报、每个路线块和每个阶段都要可独立重试；写入采用原子提交，失败不能覆盖已有的有效结果。
- 扫描、布局、OCR、组装校验、VLM 复核、导出分为独立阶段；VLM 不阻塞 OCR 全量推进。
- 批处理采用有界队列和背压，不允许一次性把所有图片或裁片装入内存。
- 同一图片或同一裁片被多个 worker 同时处理时，通过唯一键和幂等写入避免重复提交。

### 版面与画布打包

- 复用现有版面投影逻辑：红色路线块、站名行投影、站名列投影、宽列递归拆分和最后兜底拆分。
- 画布打包按真实列宽动态计算，不再固定八列；配置项包括最大列数、最大画布宽度和列间距。
- 默认基线为最多 8 列、画布宽度不超过 1000px、列间距 30px。
- 在准确率 A/B 通过后，可评估 10 列/1000px 或 12 列/1400px；未通过前不得直接作为全量默认值。
- 站名列与紧随其后的备注列尽量作为原子组打包，避免备注列跨画布。
- 画布尺寸和打包参数必须写入缓存 key；打包配置变化后旧画布缓存自动失效。
- 每个画布保留列 ID、源图坐标和列边界映射，远程 OCR 只返回相对画布的 box，本地负责加回偏移并映射到列。

### OCR 后端

- 定义统一 OCR 后端接口，输入一张或多张图片及 OCR 参数，输出每张图片的文字、框坐标和置信度。
- 本地后端继续包装现有 RapidOCR，保持现有 det/cls/rec 行为和默认阈值。
- 远程后端通过 HTTP 调用无状态 OCR 服务；远程不参与站名、备注、当前站、下站和业务解析。
- 远程请求支持一次携带多个画布，建议每批 4–8 个画布或总负载不超过约 1MB，具体以供应商限制为准。
- 远程响应必须包含每张画布的稳定 ID、文字框、置信度和模型版本；缺少坐标或置信度的供应商不满足主链路要求。
- 远程请求必须支持超时、幂等键、有限重试、退避和熔断；连续失败时对该批次切换本地 OCR。
- 远程失败、返回空结果、覆盖率不足或检测框跨列时，保留现有单列 fallback 逻辑。
- 远程和本地必须使用相同或可对比的模型版本；模型版本变化必须使 OCR 缓存失效并触发小样本回归。

### VLM 复核

- 定义 VLM 复核器接口，输入目标裁片、前后站裁片、线路号、表头下站、开往方向和 OCR 候选，输出结构化复核意见。
- VLM 只处理异常样本：低置信度、跨列、下站不一致、双向不一致、新模板和随机抽样 QA。
- 每张海报设置 VLM 最大调用数，默认不超过异常数量的一个可配置上限，避免成本失控。
- 不把整张海报发给 VLM；单次只发送目标裁片和必要邻接上下文。
- VLM 温度设为 0，提示词必须版本化；输出必须是可校验的 JSON，至少包含识别文本、备注、是否同意 OCR、置信度和原因。
- VLM 结果只作为意见：与 OCR 一致时可用于清除异常标记；不一致时进入人工复核；输出非法或低置信度时忽略。
- OCR 为空时允许 VLM 结果作为候选，但必须标记来源为 VLM-only 并进入复核，不得自动视为最终值。
- VLM 调用结果按裁片哈希、提示词版本和模型版本缓存，避免重复计费和重复等待。

### 组装、校验与来源

- 继续使用现有站名组装规则：空文本过滤、日期过滤、备注列判断、完整标注生成和当前站检测。
- 继续使用下站校验、当前站兜底和双向站序对齐；不一致项写入复核队列。
- 最终站名记录必须包含来源（OCR、OCR+VLM、VLM-only、人工）和置信度，便于审计。
- 人工修正以图片哈希、路线、方向和站序为键持久化；不以原始 OCR 字符串作为唯一键。
- 分析器继续负责最终的站点级修正、双向校验和 Excel/CSV/报告生成；批处理输出必须与现有分析器输入兼容。

### 缓存

- 布局缓存：图片哈希 + 版面算法版本。
- 画布缓存：画布哈希 + 打包参数 + OCR 参数 + OCR 模型版本。
- VLM 缓存：裁片哈希 + 提示词版本 + VLM 模型版本。
- 海报最终缓存：图片哈希 + 管线版本 + 关键配置版本。
- 所有缓存命中后都必须做结构校验；校验失败的缓存视为 miss，不得返回部分或损坏结果。
- 缓存写入采用原子方式；不得用失败结果覆盖有效缓存。

### 并发、限流与可观测性

- 布局阶段按 CPU 并行；OCR 本地后端按进程/线程配置并行；远程 OCR 和 VLM 各自使用独立并发池。
- 远程 OCR 和 VLM 都必须设置请求速率、并发上限、超时、重试和熔断策略。
- 上传带宽或远程 QPS 达到上限时采用背压，不允许无限堆积任务。
- 记录每张海报、每个路线块和每个阶段的耗时；记录缓存命中、OCR fallback、重试、VLM 调用和失败原因。
- 批次报告至少包含总数、完成数、失败数、复核数、缓存命中率、OCR 调用数、VLM 调用数和总耗时。

### 配置与安全

- 源目录、输出目录、OCR 后端类型、远程地址、模型名、并发数、画布参数、VLM 触发阈值和抽样比例均通过配置或环境变量提供。
- API 密钥只从环境变量或密钥管理读取，不写入代码、日志、规格文件或输出结果。
- 远程 OCR 和 VLM 的请求日志不得记录完整裁片内容或敏感凭据。
- 支持 dry-run 模式：只扫描和生成 manifest，不调用 OCR/VLM，用于检查输入和估算规模。

### 规模与部署约束

- 目标规模约 20GB、约 1600 张海报；系统必须支持分批、断点和增量新增。
- 远程 OCR 不建议逐张上传完整海报；优先上传裁片/画布，或把源数据一次性同步到远程 GPU 所在环境。
- 远程 OCR 和 VLM 可以是不同供应商；适配器层必须隔离其请求格式和错误模型。
- 首次全量、重跑、增量新增和断点续跑分别统计耗时，不把缓存命中后的时间当作首次识别性能。

## Testing Decisions

- 好的测试只验证外部行为：给定源目录、配置和可注入的 fake OCR/VLM，断言 manifest 状态、输出 JSON、复核队列、请求次数和缓存命中，不断言内部函数调用顺序。
- 主验收缝为批量入口。集成测试使用 1–2 张小型固定海报或裁片 fixture，配合确定性 fake OCR 后端，验证从扫描到导出的完整路径。
- OCR 后端契约测试使用本地 fake HTTP 服务，覆盖正常响应、空结果、缺少坐标、超时、429、5xx、重复幂等键和模型版本变化。
- VLM 复核器契约测试使用 fake HTTP 服务，覆盖同意、冲突、非法 JSON、低置信度、空结果和超时；断言冲突不会被静默覆盖。
- 画布打包单元测试覆盖动态列数、最大宽度、列间距、备注原子组、单列超宽和空列。
- 缓存测试覆盖命中、未命中、配置变化失效、模型版本变化失效、损坏缓存回退和并发写入。
- 状态机测试覆盖断点续跑、失败重试、重复图片去重、部分海报失败不影响其他海报。
- 解析与校验测试覆盖当前站、下站、双向站序、括号备注、日期过滤和未知模板标记。
- 回归测试使用现有安淡/安平已修正结果中可复用的站名与站序作为 golden fixture；不要求测试环境重新跑完整 20GB。
- 性能冒烟测试使用合成的 100 张海报 manifest 和 fake OCR，验证内存有界、队列背压和缓存命中率；真实远程吞吐另做基准，不放入默认 CI。
- 准确率评估独立于单元测试：使用人工标注的站名裁片集合，统计逐字准确率、站数一致性、备注正确率和 VLM 冲突率；未达到 OCR 基线前不得扩大 VLM 主识别范围。
- 当前代码库没有现成测试套件和测试先例；测试框架、fixture 和 fake 服务均为新增，但应保持最小依赖。

## Out of Scope

- 训练或微调 OCR、VLM 模型。
- 构建人工复核 UI 或多用户协作界面。
- 自动发现并完全适配所有未知站牌模板；新模板只要求被标记和隔离。
- 替换现有站名修正词典、双向校验规则和人工修正成果。
- 对外发布数据、上传到第三方业务系统或提供 API 服务。
- 供应商账号开通、GPU 机器采购、网络和计费配置。
- 保证 VLM 输出绝对正确；人工复核仍然是异常样本的最终兜底。
- PDF、AI 占位文件或其他非 JPG 输入的识别。
- 多租户、权限体系和生产级鉴权。
- 对 20GB 全量做一次性内存预加载。

## Further Notes

- 现有实测基线：安平小区 3 张海报、462 个站点、约 6 分 30 秒；动态打包实际产生 74 个站名画布，平均 7.07 列/画布，60 个画布为满 8 列。
- 同一批数据下，10 列/1000px 约 61 个画布，12 列/1400px 约 51 个画布，PNG 总字节几乎不变；因此更大画布主要减少请求数，但会增加跨列合并风险，必须 A/B。
- 按 20GB、约 1600 张估算，站名画布请求约 3–4 万次；表头 OCR 约 3 万次。VLM 只处理 1–5% 的异常样本，才能把成本和延迟控制在可接受范围。
- 安平 462 个站名裁片的精确重复数为 0，因此裁片缓存对首次全量收益很低，主要价值在重跑、断点续跑和远程重试。
- 当前机器无 NVIDIA GPU，本地 OCR 为 CPU；远程 GPU 或云 OCR 是横向扩展的主要手段。
